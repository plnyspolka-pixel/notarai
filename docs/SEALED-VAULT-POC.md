# NotarAI Sealed Vault POC (not production ready)

## What is implemented
- `static/sealed-client.mjs`: local-only-capable WebCrypto AES-256-GCM encryption and decryption with per-document 128-bit salt, per-document 96-bit random nonce and authenticated tenant/document binding (AAD). Passphrase-derived key via PBKDF2-SHA256 (600,000 rounds).
- `sealed_vault.py`: authenticated, notary-restricted *ciphertext-only* API, backed by office-partitioned storage; private `POST /api/sealed/documents`, `GET /api/sealed/documents/{uuid}`, `GET /api/sealed/context`.
- Tests: `node --test test_sealed_client.mjs`, `pytest test_sealed_vault.py` in isolated CI environment.

**Important**: this POC is entirely separate from the existing document creation / Bedrock flow, which currently processes plaintext. Envelopes must be created on a *trusted local copy* of the crypto module before upload. Do not download and execute an unverified, freshly server-served JS module if claiming the operator cannot obtain access to plaintext. Verify the build/signature first. Never submit passphrases or decrypted content to the server.

## Not security certification
- PBKDF2 and a human passphrase do not protect against well-funded offline guessing of a weak password; production design requires strong key generation, secure hardware-backed key custody, key wrapping for multiple authorized staff, password recovery/revocation, backup and device attestation.
- No secure standalone installer, signed release or trusted auto-update exists yet. Do NOT claim guaranteed zero-knowledge or confidentiality against a malicious operator that can replace client code.
- Authentication still uses the existing NotarAI middleware. `PIECZAPP_MULTI=false` is single-office local-mode and intentionally does not enforce user login; do not expose local mode to public networks.
- POC stores encrypted JSON in a single per-office file; maximum 50 documents and 4 MiB per document. Not suitable for large office archives or production load. It cannot prove the client used the intended encryption algorithm rather than fabricated envelope fields.
- No access receipt, signer, encrypted client-side filename index, independent WORM record or confirmed Ethereum anchor is generated by this route. Existing `/api/dowody` may be used independently for integrity, with a separate trusted release process.
- Even when encrypted end-to-end, the office's own device/user, malware, browser extensions, screenshots and local backups remain in the threat model. AI in Bedrock needs an explicitly separate processing mode and cannot inherit Sealed assurance.

## Manual evaluation
1. In a local secure execution context (HTTPS browser or Node with WebCrypto), import `static/sealed-client.mjs` from a versioned, trusted local copy.
2. Obtain the office `tenantRef` from an authenticated `GET /api/sealed/context` (no secret key).
3. Call `sealBytes(Uint8Array, passphrase, tenantRef)`; the result is ciphertext-only JSON.
4. POST JSON to `/api/sealed/documents`; passphrase never goes to server.
5. GET the envelope and call `openSealedBytes(envelope, passphrase)` on office's device. Wrong key or tampering must be rejected.
6. Compare the server-observed request and storage contents to prove they include ciphertext but not plaintext. Do not test with real notarial acts.

## Future work
- Move storage to per-object immutable encrypted S3 keys with tenant isolation and safe garbage collection.
- Rework encryption to random file DEK + hardware-backed office KEK and per-recipient wrapping, avoid password-only model.
- Build a signed, reproducible offline desktop client and independent verifier with pinned public keys.
- Generate digitally signed privacy receipts for the actual client cryptographic operation and publish only private salted batch Merkle roots.
